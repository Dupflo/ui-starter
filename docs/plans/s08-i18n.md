## Target story

**s08-i18n — fr/en language switch** (docs/stories.md:167-185). Complexity 1, finalisation.
The infra (routing, request config, navigation, proxy), persistence, deep fr/en parity test,
and a working Settings selector all already exist. This story closes two residual gaps only.

Acceptance criteria:

- **AC1** — a language selector toggles between fr and en. _Gap: present in Settings, absent on the public surfaces (landing, auth)._
- **AC2** — all delivered screens have their strings in fr AND en; no missing key at runtime. _Deep fr↔en parity already locked by messages.test.ts; the residual gap is a key referenced but absent from BOTH locales._
- **AC3** — the chosen language persists (cookie/URL locale). _Already works: `localePrefix: "as-needed"` + `NEXT_LOCALE` cookie set by the next-intl middleware in proxy.ts. NO work._

## The point everything turns on

The plan stands on **`LocaleMenu` being the right primitive for BOTH surfaces, and the presence-test (approach b) being the honest coverage guarantee (over source-scanning, approach a).**

Where it could be wrong, and against what to check:

- **Primitive fit on the landing header.** `LocaleMenu` is styled for a dark/pine surface (`text-paper`, `border-paper/15`; light popover `bg-paper`). If the landing header is NOT pine, the trigger is invisible. → Compare the new header's background token against `LocaleMenu`'s trigger classes (`components/ui/locale-menu.tsx:63`); keep the header pine (as the legal header is, `(legal)/layout.tsx:24`).
- **Auth-shell client/server boundary.** `auth-shell.tsx` is currently a server component (no `"use client"`). Mounting `LocaleMenu` (a client component) inside it is fine — RSC can render client children — but adding any hook/handler to AuthShell itself would break it. → Check that AuthShell gains only the `<LocaleMenu />` element, no client hooks; it stays a server component.
- **Coverage test choice (a vs b).** Approach (a) — scan source for `t("literal")` — is brittle here: the landing resolves pricing keys dynamically (`tPricing(plan.nameKey)`), which a literal scan can't see, producing false confidence. Approach (b) — per-namespace enumerated presence tests mirroring `auth.test.ts` — is explicit and maintainable, and lets us pin the dynamic pricing keys by hand. → Compare the namespaces pinned in `coverage.test.ts` against `Object.keys(fr.json)`: `auth` + `legal` are already covered by their own tests; the new file must cover the rest so every delivered namespace has a presence guarantee. The tradeoff (b requires updating the key list when a screen adds a key) is acceptable and matches the repo's existing pattern.

## Test strategy

- **Unit / message level (primary):** `messages/coverage.test.ts` — Vitest, colocated. For each un-pinned namespace, assert every referenced key exists in fr AND en (presence + parity), mirroring `auth.test.ts`. This is the AC2 hardening: a `t("x")` key absent from both locales now fails a test. Keep the existing deep parity test (`messages.test.ts`) as the fr↔en symmetry guard.
- **Component level (AC1 mount):** if a lightweight render assertion is cheap and matches existing component-test conventions, assert `AuthShell` and the landing render a `LocaleMenu` trigger (role/aria-label `localeSwitcher.label`). Otherwise rely on the existing page/component test suites not regressing — the mount is a static child render, low risk.
- **AC3:** no test rebuilt; documented in the coverage test header as delivered by routing + cookie (out of scope).
- **Regression gate:** full `vitest` suite green (12 existing message/page tests + component tests), and `npm run build` passes the `check-design-tokens` prebuild (proves the new header is tokens-only).
