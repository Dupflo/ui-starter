# Research — Story s08-i18n

## The five structuring facts

1. **A working language selector already ships — inside Settings.** `components/app/settings-form.tsx:220-236` renders a `Select` on `t("interfaceLanguage")` that calls `router.replace(pathname, { locale })` from `@/i18n/navigation`. AC1 ("a selector toggles fr/en") is therefore already met on the authenticated surface. It is NOT met on landing or auth (no selector rendered there).
2. **The two dedicated switcher primitives are orphaned.** `components/ui/locale-switcher.tsx` and `components/ui/locale-menu.tsx` are fully built and correct, but a repo-wide grep finds **zero** render sites (`grep -rn "LocaleSwitcher\|LocaleMenu\|locale-switcher\|locale-menu"` → only their own definitions). They are dead code today. Wiring one of them onto landing/auth is the natural way to close the AC1 gap on public surfaces.
3. **Persistence (AC3) is URL-prefix + cookie, already wired.** `i18n/routing.ts:3-8`: `locales ["fr","en"]`, `defaultLocale "fr"`, `localePrefix "as-needed"` (fr unprefixed, en → `/en`). The next-intl middleware runs in `proxy.ts:6,17` and also sets the `NEXT_LOCALE` cookie; `router.replace(pathname, { locale })` navigates to the prefixed URL, so the choice persists across navigation and reload. No work needed for AC3.
4. **Deep fr/en parity is ALREADY guaranteed by a recursive test.** `messages/messages.test.ts:6-33` flattens both JSONs to nested key paths (`a.b.c`) and asserts the two sets are identical — not just top-level namespaces. Plus `auth.test.ts` and `legal.test.ts` assert specific used-key presence + no killed-domain branding. All 12 tests pass. AC2's "no missing key one side vs the other" is structurally locked.
5. **The real AC2 residual gap is used-but-missing, not fr↔en asymmetry.** The parity test proves fr and en agree with _each other_; it does NOT prove that every key a `t("...")` call references actually exists in the JSON. No test currently cross-checks code→messages. This is the one class of runtime "missing key" the current suite can't catch — the minimal s08 hardening target.

## Target story

**s08-i18n — fr/en language switch** (docs/stories.md:167-185). Complexity scored **1**. Finalisation story: does not rewrite upstream screens, verifies + completes their i18n coverage; s03/s04/s06/s07 own their keys, s08 owns the fr+en coverage guarantee. Depends on s03 + s04 + s07 (all merged).

Acceptance criteria:

- **AC1** — a language selector toggles between fr and en.
- **AC2** — all delivered screens (landing, auth, dashboard) have their strings in fr AND en; no missing key at runtime.
- **AC3** — the chosen language persists (cookie/URL locale).

## Anchor points

Where s08 would plug in, per surface:

- **Landing** — `app/[locale]/page.tsx:34-88` is a bare `<main>` with hero/pricing/CTA and **no header/nav bar**. There is no existing mount point for a switcher; adding one means adding a small header (or dropping the switcher into the hero). AC1 gap on this surface.
- **Auth** — `components/auth/auth-shell.tsx:12-24` (pine canvas + centred card, used by login/signup; forgot/new-password use their own pages). No switcher rendered. AC1 gap.
- **Legal** — `app/[locale]/(legal)/layout.tsx:24-36` has a real `<header>` (logo + back-home link) — a clean mount point if legal is counted as a public surface (story lists landing/auth/dashboard, not legal).
- **Dashboard/app** — `components/app/app-header.tsx:32-37` right-side action zone + `DarkModeToggle`; the actual selector lives one level deeper in Settings (`settings-form.tsx:220-236`). AC1 already met here.
- **Parity test** — `messages/messages.test.ts` is the artifact to strengthen for the used-but-missing dimension.

## Verified APIs / functions

- `routing` — `i18n/routing.ts:3` (`defineRouting`, `localePrefix: "as-needed"`); `routing.locales` = `["fr","en"]`; `LOCALE_LABELS` (routing.ts:12-15).
- `useRouter().replace(pathname, { locale })` + `usePathname()` from `@/i18n/navigation` — the locale-switch idiom, used in `settings-form.tsx:228`, `locale-switcher.tsx:26`, `locale-menu.tsx:50`.
- `getTranslations(ns)` / `useTranslations(ns)` — every delivered screen resolves strings through these (verified: admin, dashboard, settings, legal×4, login, signup, forgot, new-password, landing, pricing, cookie-banner, app-sidebar, dark-mode-toggle all call one of them).
- `setRequestLocale(locale)` — called in every server page/layout for static-render correctness.
- `flatKeys(obj, prefix)` — `messages/messages.test.ts:6-17`, the recursive flattener already used for deep parity.

## Traps & constraints

- **Do not rewrite upstream screens** (finalisation only). The screens are already fully i18n-wired — a hardcoded-string scan of the app shell (`app-sidebar`, `app-shell`, `mobile-sidebar`, `dark-mode-toggle`) and auth forms found none; `google-button.tsx:19,72` takes its label as a prop (the translated `auth.google` key), not a literal. No AC2 defect from hardcoded strings was found.
- **fr+en updated together** — any key added must land in both files (the parity test fails otherwise). This is the guard s08 owns.
- **Tokens-only for any switcher UI** (ADR 002): the existing `locale-switcher.tsx` / `locale-menu.tsx` already use only token classes (`text-paper`, `bg-pine`, `ring-lime`, `border-line`…) — reuse them, don't restyle with raw values. `check-design-tokens` runs at prebuild.
- **`localePrefix: "as-needed"`** means fr has no prefix — any manual URL/link logic must go through `@/i18n/navigation`, never `next/link` (project law).
- **Existing tests to not regress**: 12 message tests + `app/[locale]/page.test.ts` + component tests. A strengthened parity test must stay green against the current JSONs (they are already consistent).
- **The parity test's blind spot**: it validates fr↔en symmetry, not code→JSON. A key referenced by `t("x")` but absent from _both_ locales would pass parity yet render the raw key at runtime. That's the gap to close if AC2 is read strictly ("no missing key at runtime").

## Open questions

- **AC1 scope**: does "a language selector" require the selector to be reachable _from the public surfaces_ (landing + auth), or is the Settings selector (authenticated only) sufficient? The story's own wording ("all delivered screens: landing, auth, dashboard") strongly implies the switcher must be reachable on landing and auth too → wire `LocaleMenu` (landing/auth-dark-header variant) or `LocaleSwitcher` onto those surfaces. **Recommend treating landing + auth as in-scope for AC1.** Resolve at planning.
- **Where to mount on landing**: the landing has no header today. Add a minimal header bar, or place the switcher in-hero? A design-system-consistent minimal header is the cleaner call but is the only "new UI" in the story.
- **Legal pages**: counted as a delivered surface? Story lists landing/auth/dashboard only — likely leave legal as-is (it already has a header if a switcher is later wanted).
- **Used-but-missing enforcement**: strengthen `messages.test.ts` to also assert every `t()`-referenced key exists (static extraction is brittle with dynamic keys like `plan.nameKey`), or accept the deep-parity + per-namespace presence tests (auth/legal) as sufficient? Leaning: extend the presence-test pattern (auth.test.ts / legal.test.ts) to the remaining delivered namespaces (home, pricing, dashboard, appNav, settings, forgot, newPassword, localeSwitcher) rather than attempt full static `t()` extraction.

## Real complexity

**Scored 1 in docs/stories.md — confirmed 1 (finalisation), but not zero.** The infra, persistence, deep-parity test, and a working selector all already exist, so the story is genuinely small. The only real work is:

1. **Wire a selector onto the public surfaces (landing + auth)** — reuse the orphaned `LocaleMenu`/`LocaleSwitcher` primitives; landing needs a minimal header to host it (the one bit of new-but-trivial UI).
2. **Strengthen the coverage guarantee** — extend the presence-test pattern to the remaining delivered namespaces so a used-but-missing key can't slip through (fr↔en parity is already locked).
3. **Fill any gap surfaced** — none found in this pass; the JSONs are already consistent and no hardcoded UI string remains.

No split needed. The risk is not technical difficulty but scope creep (adding a marketing header, restyling switchers) — hold the line on finalisation. The main artifact is a strengthened test plus a few lines of wiring.

## Split proposal

Not required (verdict 1). Single story, single cycle.
